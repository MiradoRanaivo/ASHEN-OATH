# ASHEN OATH API

Backend Node.js + Express + TypeScript. The API is separated from the Phaser client so that gameplay remains available when the API is offline.

## Requirements

- Node.js LTS
- npm
- MySQL 8.0.16 or newer

## Local setup

The MySQL database `ashen_oath` must exist before running migrations. If you have not created it yet, connect to MySQL and execute:

```sql
CREATE DATABASE ashen_oath CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

Then configure the connection:

```bash
cd server
cp .env.example .env
```

Edit `.env` and set `DB_PASSWORD` to the password of `DB_USER`. Install dependencies, apply migrations, and start the API:

```bash
npm install
npm run db:migrate
npm run dev
```

Health check: `GET http://localhost:3000/api/health`. The health route intentionally does not require a database query, so basic API availability remains independent from database availability.

## Database

- `users` stores account identifiers and password hashes only; plaintext passwords must never be stored.
- MySQL's `utf8mb4_0900_ai_ci` collation makes username and email uniqueness case-insensitive.
- User and session identifiers are UUID strings generated by the application.
- `sessions` stores only a SHA-256 hash of the opaque session token, never the browser token itself.
- Migrations are SQL files in `src/db/migrations` and are tracked in `schema_migrations`.
- The migration runner uses a MySQL advisory lock to prevent concurrent migration runs. MySQL DDL can commit implicitly, so a migration is recorded only after all its statements succeed; migration files should be written to be safe to retry.

## Authentication architecture (implementation roadmap)

Authentication will be added in small, independently tested increments:

1. API foundation and environment validation (completed).
2. MySQL connection, migrations, and user/session schema (current step).
3. Registration with input validation and Argon2id password hashing.
4. Login and opaque server-side sessions.
5. HttpOnly cookie handling, authentication middleware, current-user and logout endpoints.
6. Security tests, rate limiting, CSRF protection, and client integration.

The planned browser authentication mechanism is a server-side session identified by a cryptographically random opaque cookie. Passwords will never be stored in plaintext. Session identifiers and secrets must never be exposed to the Phaser client or committed to Git.

## Configuration

Copy `.env.example` to `.env`. Never commit real environment files or production secrets.
